Requested to investigate repeated PBP MCP authorization failures. The cause of
the affected users' failures has NOT been established. A working login from
another account, a simulation, or a session's Created/Last used dates do not
establish the reason an affected user's renewal failed.

AUTOMATIC LOGGING

Enabled automatically, including in packaged apps with debug mode off.
The private auth-debug build enables runner debug logging by default. Its
Debug page has PBP Authorization and Throttling tabs, with authorization first
and selected by default. The authorization tab has an Open log folder button
for manually sending the files through Discord. No logs are uploaded.
Normal release builds keep their existing throttle debug page.

File: pbp-auth-debug.log beside config.json in the app's data directory.
Normal installed locations:
  macOS: ~/Library/Application Support/missions-v3-mcp/
  Windows: %APPDATA%\missions-v3-mcp\
Development/CLI: the active configuration directory (PBP_CONFIG_DIR or cwd).
The standalone pbp-mcp CLI defaults to ~/.pbp-mcp/pbp-auth-debug.log.

The desktop process and runner append to the same log. Process IDs, runtime
IDs, roles, sequence numbers, request IDs and token fingerprints identify who
used which credentials. Logs rotate at approximately 5 MiB, retaining .1 and
.2 backups. New logs are created with owner-only permissions where supported.

Successful token reads, HTTP calls and proactive renewals are NOT written to
disk. A rolling in-memory buffer keeps up to 120 preceding events, capped at
256 KiB per process. A real failure OR an authorization browser launch writes
a PBP AUTH INCIDENT BEGIN block with that context and runtime information.
While a report is open, only failures, auth recovery/login steps and the final
successful authenticated request are written. Ordinary calls and token reads
stay buffered. Recovery closes the report and disk logging goes quiet again.
Normal proactive renewal starting is not a failure.

Every popup report includes its initiating call stack, reason (renewal_failed,
watch_auth_error, or startup_or_requested_login), triggering watch error where
applicable, credential fingerprints/expiry/file state, popup eligibility and
actual browser launch result. Even a direct library/CLI browser launch writes
a report, so an unexpected authorization window cannot silently go unrecorded.

Captured: token presence, file path/stat/read/write failures, credential and
client fingerprints, granted scopes, expiry timestamps, decoded JWT timing
fields (not signature validation), local time/server Date/timezone, metadata
discovery and selected endpoints, the failing request/response status,
provider response text in rawResponse (full text with original whitespace/SSE
framing, without the former 16,000-character cutoff), OAuth error codes
and descriptions, Retry-After, WWW-Authenticate, provider request IDs, network
error causes/stacks, refresh attempts, replacement refresh-token fingerprints,
credential changes during a refresh, browser launch outcomes, callback state
matching, token exchange/save outcomes, and watcher recovery decisions.
Response headers and status text are included. Credential values are still
redacted, including in rawResponse; exact text means everything except secrets.

Raw access/refresh/registration tokens, authorization headers, auth codes,
PKCE secrets and callback state values are redacted. Successful mission/NFT
payloads are not dumped; their HTTP outcome and credentials used are logged.

REQUESTED TEMPORARY MITIGATION

Only opening another authorization window is limited: at most one window per
five minutes normally or two minutes in Mission Mode, measured from the last
browser launch. The timestamp is shared through token.json.auth-popup.json.
An atomic cross-process claim prevents the desktop and runner from opening
two windows at once. A pending window is reused until that login completes.
Token renewal is NOT gated by this window interval. Existing refresh attempts
continue on subsequent mission/watch requests, including while a login window
is pending. The first renewal attempt is immediate; after a failed attempt,
the client waits at least ten seconds before its next attempt, including
across recovery batches. This retry wait is logged as client.refresh.retry_wait.
A late login timeout does not replace a newer successful renewal
with an expired status. Mission/watch/claim timing is unchanged.
The superseded token.json.auth-retry.json file is no longer read or written.
This mitigation does not establish or repair the underlying reported cause.
